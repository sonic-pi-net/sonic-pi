# Plan: the web GUI, from Sonic Tau and Sonic Pi v5

Give web-sonic-pi a real GUI. Not a verbatim copy of anything: take each
part from where it is best today.

| Part | Taken from |
|---|---|
| Layout, the editor shell, scopes | Sonic Tau |
| Themes and how they apply, syntax highlighting, autocomplete, docs | native Sonic Pi v5 (the Qt GUI) |
| Running code, sound | the mruby runtime and SuperSonic, as now |

This supersedes `PLAN-app-page.md`, which copied the wrong project
(`next-gen/sonic-tau`, a small experiment that shares the name).

## Where the sources are

* **Sonic Tau** — hosted at https://sonic-pi.net/tau. Source:
  `~/Development/tau-state/app/src` at 93f81f8 (`index.html`, `app.js`,
  `editor.js` on CodeMirror 6, `share.js`). The Tauri app
  `~/Development/sonic-tau` carries the same GUI built.
* **Native Sonic Pi v5 GUI** — `~/Development/sonic-pi/app/gui` on branch
  `vst-host-2026-08-31` at 1f406654f, 38 commits ahead of `origin/dev` and
  **not pushed**. The parts that matter:
  * highlighting: `widgets/sonicpilexer.cpp` (QScintilla's Ruby lexer,
    coloured from `model/sonicpitheme.cpp`: light, dark, high contrast,
    mild dark, phosphor, signal)
  * autocomplete: `utils/completion_context.cpp` (scan the line to the
    caret, derive the call context, resolve what kind of value an argument
    slot takes, which opts a function accepts, whether the caret is at an
    opt key), `utils/scintilla_api.cpp` (the candidate lists by context,
    synth in effect at the caret, opt ranges and enum values, chord and
    scale intervals), `widgets/completionpopup.cpp` (the popup: a detail
    pane with the docstring and usage card, a slider for bounded opts with
    live preview in the buffer, enum values with shape diagrams, note,
    chord and scale previews, sample audition, screen-reader
    announcements), and tables generated by `qt-doc.rb`
    (`completion_argkinds.gen.h`, `completion_fnopts.gen.h`,
    `completion_optowners.gen.h`)
  * docs: `etc/doc/generated/native/reference/{lang,synths,fx,samples}.json`
    and per-language tutorial JSON (blocks: heading, prose, list, code
    marked runnable, image), rendered by `utils/tutorialdocs.cpp` with
    `theme/*/doc-styles.css`
  * behaviour pinned by `app/gui-tests/` (completion context, detection,
    ranking, fn opts, opt owners, arg kinds, popup selection and a11y)

**None of the reference JSON or the generated completion tables exist at
v5.0.0**, the oracle's pin. They are only on that unpushed branch. But the
doc system they are generated from is already there at v5.0.0: every synth
opt has its constraints, bounds (min, max, exclusivity, enum options),
slidable and range. Against the branch, v5.0.0 documents 241 functions to
254 and tags 20 with arg kinds to 27; the difference is tracks and Link
audio, which the web build does not have. **Decided: the language oracle,
and so the editor's knowledge, is v5.0.0.**

* **Native themes** — `app/gui/model/sonicpitheme.cpp`: six schemes (light,
  dark, high contrast, and mild dark, phosphor and signal derived from a
  neutral base), each a map of named colours (`Foreground`, `PaneBackground`,
  `SymbolForeground`, `Scope`, `LogBackground_3`, `CuePathBackground` …);
  derived roles (soft, muted, faint and ghost foreground, accent tints);
  global transforms over every resolved colour (hue rotation, hue spread,
  monochrome, invert). Applied by filling colour tokens into
  `theme/app.qss` and the per-scheme `theme/*/doc-styles.css`.

## Principles

* **No tree-sitter.** Sonic Pi code is Ruby. Highlighting is CodeMirror's
  Ruby mode plus a thin Sonic Pi layer (symbols, the language's function
  names, demoted keywords), coloured the way the native lexer colours.
* **Knowledge comes from Sonic Pi, generated.** Function names, args, opts,
  ranges, enum values, arg kinds, docs: all generated from Sonic Pi's Ruby
  doc system by a script modelled on `qt-doc.rb`, not written by hand and
  not copied from Sonic Tau's tables.
* **Port behaviour, pinned by tests.** The completion logic is ported from
  C++ to JS with the native `gui-tests` cases ported alongside, so the web
  editor completes as the native one does, case for case.
* **One engine seam.** The GUI calls `web/sonic_pi.js` (`loadRuntime`,
  `Bridge`, `LiveSession`); nothing in the GUI knows about mruby.

## Phases

### 0. Data: generate the editor's knowledge

* `scripts/gen-editor-data.rb`, modelled on `qt-doc.rb`'s reference and
  completion sections, writes `web/data/`:
  * `lang.json`, `synths.json`, `fx.json`, `samples.json` in the native
    reference shape (key, title, doc html, opts with default, doc, min, max,
    exclusive edges, slidable, enum options)
  * `completion.json`: arg kinds per function, opts per function, opt
    owners, chord and scale intervals
  * tutorial JSON per language, in the native block shape
* Decide the source (see open choices): the oracle at v5.0.0, or the local
  branch. First step either way: run the generator against v5.0.0 and list
  what the doc system there lacks (`bounds`, enum `options`, arg kinds),
  so the gap is known, not guessed.

### 1. Themes and layout

* **Themes, as native does them.** `scripts/gen-themes.mjs` reads the
  scheme maps out of `sonicpitheme.cpp` and writes `web/theme/themes.json`,
  so the web themes are native's, and follow native when it changes. A
  small `web/theme/theme.js` ports the rest: derived roles, the hue
  rotation, hue spread, monochrome and invert transforms, and filling the
  colours in as CSS custom properties named after the native keys
  (`--Foreground`, `--SymbolForeground` …). The page's stylesheet is written
  against those properties, following `app.qss`; docs use the three
  `doc-styles.css` with their tokens filled the same way.
* All six schemes, with native's prefs: scheme, hue, spread, monochrome,
  invert.
* **Layout from Sonic Tau:** the toolbar (run, stop, font size, prefs,
  help); the scope strip; editor column; output, errors, log and cue panes;
  the resizable dividers.
* Replaces the lookalike `web/index.html`. `web/specs.html` stays, restyled
  with the same properties.

### 2. The editor shell

* CodeMirror 6 set up as Sonic Tau sets it up: keymaps, buffers kept in
  local storage, comment toggle, font size, the statement flash, error
  gutter.
* Highlighting: `@codemirror/legacy-modes` Ruby through `StreamLanguage`,
  with a Sonic Pi token layer on top for what the native lexer
  distinguishes.
* Built with esbuild into `web/`; `scripts/build-web.mjs` runs it.
  CodeMirror comes from npm (`package.json` gains the `@codemirror/*`
  packages and esbuild).

### 3. Autocomplete

* Port `completion_context.cpp` and the context logic of
  `scintilla_api.cpp` to `web/editor/completion.js`, fed by
  `completion.json` and the reference JSON.
* Port the `gui-tests` completion cases to `node --test` and keep them
  passing.
* The popup, as a CodeMirror completion with a custom renderer, in order of
  value: the detail pane (docstring, usage card); sliders for bounded opts
  with live preview in the buffer; enum values; sample audition through the
  bridge; note, chord and scale previews; shape diagrams last.
* Accessibility is not optional: the popup announces the selection as the
  native one does (`completionpopup_a11y`).
* Contexts follow what the web build supports. MIDI ports and params
  complete, from SuperSonic's web MIDI. OSC does not exist on the web, so
  OSC paths and ports are not offered; cue paths still come from the
  program's own cues. Link audio peers and channels are native only.

### 4. Docs

* A docs pane rendering the reference JSON (lang, synths, fx, samples) and
  the tutorial, styled from the native `doc-styles.css`, per theme.
* Runnable code blocks run through the live session; "copy to buffer" puts
  them in the editor.
* Entries the runtime does not support yet are marked, linking to the spec
  browser, rather than hidden.

### 5. Scopes

* The main scope from Sonic Tau: an `AnalyserNode` on SuperSonic's output
  (`engine.node`), with its trail, glow and line-width prefs.
* Per-live_loop scopes need audible `with_fx` routing, since each loop feeds
  a `scope_out` fx; they wait for that and are listed as a follow-up.

### 6. Running

* Run, stop, errors, output, log and cues through `LiveSession`, as the
  current app does, into Sonic Tau's panes.
* Flashes need a line per record; the runtime adds the program line to its
  records (backtrace at record time, measured for cost), and the editor
  flashes that line.

### 7. Verification

* The ported completion tests (`node --test`).
* A Playwright run over the GUI: themes switch; typing `use_synth :` offers
  every synth; `play 60, ` offers that synth's opts with ranges; a slider
  changes the buffer; the docs pane opens an entry; a tutorial block runs;
  run, flash, stop; the scope draws.
* The spec suite through the wasm and live mode, unchanged.

## Status (2026-09-14)

Built and checked (`node --test app/test/*.test.mjs`, 51 cases; `scripts/browser-check.mjs`, 26 checks):

* **Phase 0.** `gen-editor-data.rb` also writes quickstart cards and doc images; `gen-runtime-support.mjs` asks the runtime what it lacks.
* **Phase 1.** Native's six schemes and transforms (`app/src/theme.js`), Sonic Tau's layout (`app/src/index.html`, `style.css`), prefs for scheme, hue, spread, monochrome, invert.
* **Phase 2.** CodeMirror shell with ten buffers, Tau's keys, native's Alt+M re-indent, Ruby highlighting in native's lexer keys (`highlight.js`).
* **Phase 3.** `completion/context.js` and `api.js` port native's context and `completionsFor`; the popup has the detail pane, sliders editing the buffer, enum values, notes on a piano, chords and scales lit, synth, FX and sample audition. Native's context, detect, rank, fn-opts and owner-opts tests are ported.
* **Phase 4.** Docs pane: tutorial, examples, synths, FX, samples, lang; instrument pages with dials, the generated program, play and a QWERTY piano; functions the runtime lacks are marked. Quickstart cards play with their own scope, insert and copy.
* **Phase 5.** Main scope with wave, stereo and Lissajous views.
* **Phase 6.** Run, stop, errors with their line marked, log, cues (from `cue` and MIDI in), share links, a whole-buffer run flash.

Since then (2026-09-15):

* **The runtime's gaps.** control, kill, set and get, every MIDI out verb, link and set_link_bpm!, rings and lists (spread, range, line, knit, bools, stretch, halves, doubles), theory (chord_invert, chord_degree, degree, note_range, note_info), tunings, with_swing and tuplets, the current_* getters, asserts, map and vector, spark. New specs pin each against the oracle, whose harness now records control, kill and MIDI sends. 220 of 237 documented functions run; the other 16 cannot on the web (OSC, files, synthdefs, live audio) and say so.
* **Lines flash.** Live records carry the program line they came from (read from the mruby call stack in the C seam), and the editor flashes that line when the sound plays, writing the values it played after it.
* **Threads.** A gutter dot marks the line each thread waits at. The Threads view draws every thread as a lane: notes by pitch, samples, controls, MIDI, sleeps, waits on sync, cues between threads; and a table of each thread's state, line, beat, tempo and rate.
* **MIDI out** goes through Web MIDI at each message's time; incoming MIDI shows as cues.
* **Processes.** The Threads view opens on a process tree drawn as native's scsynth node tree is (nodetreegraph.cpp: level-by-depth layout, viscous easing by kind, S-curve edges, kind colours), for threads: the session, its runs, each run's main thread and what it spawned. Nodes show state (sleeping, waiting on sync, waking, done, failed, stopped) and redefinitions. It reads the runtime's process table, rows of doubles on the wasm heap (sp_process_table), every frame; names come once per thread.

* **Performance data.** A flight recorder (app/src/flight.js) samples SuperSonic's metrics (glitches heard, bundles played late, drops, queue depths), the runtime's timings (each sound's headroom, tick cost, how late ticks wake) and the page's (long tasks, frame gaps, each view's draw time, memory) ten times a second over the last five minutes, marks glitches, late bundles, drops, stalls and "I heard that" (Cmd/Ctrl+Shift+H), and saves a report with the programs and the records around each mark (Cmd/Ctrl+Shift+S). `scripts/perf-check.mjs` is the repeatable load test: the runtime's CPU cost per second of music under Node, and each program's steady state and Run/Stop in headless Chromium.

* **Real tracks start.** A track by DJ_Dave did not play: `String#ring` was missing, FX put `reps` in the wrong place among their args, and mruby's parser gave a `do` block after a call on a parenthesised command (`with_fx :echo, mix: (line 0.1, 1, steps: 128).mirror.tick do`) to the call rather than to `with_fx`, so the FX body never ran. `runtime/patches/mruby-parser-do-block.patch` brings CRuby's rule for this into mruby's parser; it passes mruby's own tests and matches CRuby on every binding case tried. The whole track is now a spec.

* **Piano roll.** A third Threads view (`app/src/piano-roll.js`) draws the notes as a DAW draws MIDI. There's a keyboard down the side with a row per semitone, and time moves across with the clock. Each note is a bar on its pitch's row, as long as its envelope: bright while held, fading through its release. The synth's default envelope is in beats, at the tempo the thread's sleeps tell. A `control` bends the bar along its slide, a `kill` or Stop cuts it short, and MIDI note_on/note_off pair up. Samples get drum-map rows. Keys light in the playing thread's colour, the grid counts bars from one thread's beats, pointing at a note names it, its synth and its line (click to jump there), and thread chips hide or show each thread. `scripts/perf-check.mjs` has a piano roll scenario.

* **Sounds cross as OSC.** The runtime encodes each sound (`/s_new`, `/n_set`, `/n_free`) as the bundle scsynth plays, in C (`runtime/host/sp_host.c`, "The audio stream"), into an outbox the page reads after each call and hands to SuperSonic as it is. Each bundle is framed with the synthdef and buffer it needs, so the page holds it back only while those load. The runtime numbers synthdefs and sample buffers itself and tells the page on first use. Bundles are byte-identical to SuperSonic's `encodeBundle`, and `live-check.mjs` decodes the stream (`web/osc.js`) and checks every sound against its record on every spec. Records for the page cross as OSC too: each is a `/sonic-pi/<kind>` message (the thread's uid, the record's time, job and line, then the kind's fields), encoded in C from the values the scheduler passes (`Native.gui`), and read back by `web/gui-stream.js` into the same records, in trace key order. A thread's id and name come once, when it starts. The page's status comes from the binary process table. No JSON crosses in a live session now; traces keep it. A `play` went from about 1,130 allocations in mruby to 44, a `sleep` from 551 to 14, and the dense load test's runtime cost from about 48 ms to 7 ms per second of music.

Not done:

* The popup's accessibility follows CodeMirror's ARIA listbox, not native's spoken announcements.
* A tempo and beat readout: the runtime's `:link` timeline does not read SuperSonic's clock.
* Incoming MIDI reaches the Cues pane but not the program (no sync on /midi cues yet).
* The spec browser keeps its own styling.

## What the web build supports

These come from SuperSonic's web build and shape what the GUI offers:

* **MIDI in and out: yes.** Web MIDI through SuperSonic. The GUI needs a
  port list and enable control (Sonic Tau has one), and MIDI completions.
  The runtime's MIDI verbs and incoming MIDI as cues are their own step.
* **Link: in shape.** Not Ableton Link on the network, but its model: one
  global timeline, shared by default by every thread. The GUI shows its
  tempo and beat; `use_bpm :link` behaviour follows that timeline.
* **OSC in and out: no.** There is no OSC on the web. The GUI offers no OSC
  panes, prefs or completions; `osc` and `osc_send` should fail with a clear
  message rather than silently.

## Out of scope for now

* Per-loop scopes and audible FX (need `with_fx` routing).
* Track and plugin completions (native only).
* The runtime's MIDI verbs and MIDI-in cues (the GUI side is in scope).
* Translations beyond English (the generator can emit them later).
